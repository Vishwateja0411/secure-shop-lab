# LAB-010: Insecure Session Management

## Overview
* **Vulnerability Name**: Insecure Session Tokens & Missing Cookie Security Flags
* **Vulnerability ID**: LAB-010
* **OWASP Category**: A07:2021 — Identification and Authentication Failures
* **Location in Source Code**: `backend/app/auth/session.py`

---

## Why It Is Vulnerable (Root Cause)
1. **Predictable Session Tokens**: In vulnerable mode, session tokens are constructed from base64-encoded user IDs and static strings:
   ```python
   token = "sess_" + base64.b64encode(json.dumps({"uid": user_id}).encode()).decode()
   ```
2. **Missing Cookie Security Attributes**: The `session_token` cookie is issued without `HttpOnly`, `SameSite`, or `Secure` flags:
   ```python
   response.set_cookie(key="session_token", value=token, httponly=False, samesite="none")
   ```
   Because `httponly=False`, client-side JavaScript can read `document.cookie`, allowing any Stored or Reflected XSS flaw (`LAB-003`, `LAB-004`) to immediately exfiltrate the active user session.

---

## Security Impact
- **Session Hijacking via XSS**: Any cross-site scripting flaw can access and steal the cookie.
- **Session Forgery**: Attackers can forge a session token for user ID 1 (`admin`) simply by base64-encoding `{"uid": 1}`.
- **Session Fixation**: Sessions do not expire or revoke properly upon logout.

---

## How to Reproduce Locally
1. Start the lab in vulnerable mode (`SECURE_MODE=false`).
2. Log in as user `alice`.
3. Open the browser Developer Tools -> Application -> Cookies.
4. Examine the `session_token` cookie:
   - Notice that the `HttpOnly` checkbox is unchecked.
   - Notice the token format: `sess_eyJ1aWQiOiAyLCAibW9kZSI6ICJpbnNlY3VyZV9sYWIifQ==`.
5. In the Developer Console, execute:
   ```javascript
   console.log(document.cookie);
   ```
   The cookie is fully accessible to JavaScript.
6. Decode the token value in the console:
   ```javascript
   atob("eyJ1aWQiOiAyLCAibW9kZSI6ICJpbnNlY3VyZV9sYWIifQ==");
   ```

---

## Expected Insecure Behavior
The session token is easily decoded/forged, and client scripts can access it directly due to the missing `HttpOnly` flag.

---

## Secure Remediation
1. **Cryptographic Entropy**: Generate 256-bit cryptographically secure random session tokens (`secrets.token_urlsafe(32)`).
2. **HttpOnly Cookie Flag**: Prohibit JavaScript access to the cookie (`httponly=True`).
3. **SameSite Cookie Attribute**: Enforce `SameSite=Lax` or `Strict` to prevent CSRF cross-origin leakage.
4. **Server-Side TTL & Invalidation**: Maintain session timestamps with idle and absolute expiration timeouts.

---

## Secure Code Example
```python
# Secure session creation:
token = secrets.token_urlsafe(32)
ttl = 3600  # 1 hour

SESSION_STORE[token] = {
    "user_id": user_id,
    "expires_at": time.time() + ttl
}

response.set_cookie(
    key="session_token",
    value=token,
    httponly=True,
    samesite="lax",
    secure=False,  # Set to True under production HTTPS
    max_age=ttl
)
```
