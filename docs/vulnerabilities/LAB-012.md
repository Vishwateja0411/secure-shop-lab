# LAB-012: Race Condition (Concurrency Control & Double-Claim)

## Overview
* **Vulnerability Name**: Time-of-Check to Time-of-Use (TOCTOU) Race Condition
* **Vulnerability ID**: LAB-012
* **OWASP Category**: A04:2021 — Insecure Design / Concurrency Flaws
* **Location in Source Code**: `backend/app/api/cart.py` (`POST /api/cart/claim-promo`)

---

## Why It Is Vulnerable (Root Cause)
The promotional credit claiming endpoint implements a non-atomic "check-then-act" pattern:
1. **Check**: It inspects `if current_user.promo_claimed: return error`.
2. **Context Switch / Async I/O Delay**: A microsecond processing window exists (e.g. `await asyncio.sleep(...)` or database query latency).
3. **Act**: It sets `current_user.promo_claimed = True` and increments the user's wallet balance by $50.00.

Because the check and state modification are not bound by an atomic database transaction or row-level lock (`SELECT ... FOR UPDATE`), multiple concurrent requests arriving during the race window all observe `promo_claimed == False` and each successfully awards $50.00 credit.

---

## Security Impact
- **Financial Exploitation**: Users can duplicate one-time rewards, promotional gifts, or drain account balances through concurrent API calls.
- **Inventory Overselling**: Concurrent checkout requests can buy items beyond available stock.

---

## How to Reproduce Locally
1. Start the lab in vulnerable mode (`SECURE_MODE=false`).
2. Log in as user `bob`.
3. Navigate to the **Profile** view.
4. Click the button: **⚡ Simulate Concurrent Race (LAB-012)**.
5. This sends 5 concurrent requests in parallel via `Promise.allSettled()`.
6. Observe the wallet balance increase by $150–$250 instead of the allowed one-time $50.00!

---

## Expected Insecure Behavior
Multiple concurrent requests execute the "Act" step simultaneously, awarding the promo credit multiple times to a single user.

---

## Secure Remediation
1. **Atomic SQL Updates**: Use a conditional SQL update statement that tests and flips the boolean flag in a single atomic database operation:
   ```sql
   UPDATE users SET promo_claimed = TRUE, balance = balance + 50
   WHERE id = :uid AND promo_claimed = FALSE;
   ```
   If `rowcount == 0`, another transaction already claimed the reward, and the current request is safely rejected.
2. **Pessimistic Row Locking**: In complex transactions, use `SELECT * FROM users WHERE id = :uid FOR UPDATE` to lock the target record until the transaction completes.

---

## Secure Code Example
```python
# Secure atomic implementation in backend/app/api/cart.py
result = db.execute(
    text(
        "UPDATE users SET promo_claimed = TRUE, balance = balance + 50 "
        "WHERE id = :uid AND promo_claimed = FALSE"
    ),
    {"uid": current_user.id}
)
db.commit()

if result.rowcount == 0:
    raise HTTPException(
        status_code=status.HTTP_400_BAD_REQUEST,
        detail="Promotion already claimed."
    )
```
